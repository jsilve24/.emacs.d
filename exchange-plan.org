#+title: Exchange calendar write-back plan
#+startup: overview

* Goal

Add a safe two-way synchronization between
=~/Dropbox/org/calendar.org= and the dedicated =EmacsSync= calendar in the
PSU Microsoft Exchange account.

Allow events created or edited on either side to propagate to the other while
preserving the current read-only import of the default Exchange calendar and
avoiding duplicates or accidental deletion of unrelated appointments.

* Implemented href-aware synchronizer (2026-10-05)

The original org-caldav sync engine is not compatible with DavMail/Exchange:
DavMail accepts a client-selected resource name on creation but returns a new
Exchange =AAMk...EML= href.  Org-caldav assumes the Org ID, iCalendar UID, and
CalDAV resource name are identical.  On the second sync it therefore imported
the Exchange resources as new events and treated the original Org entries as
remote deletions.

The damaged local file was restored byte-for-byte from the clean pre-sync
backup.  The damaged copy and mixed-ID org-caldav state were retained for
forensics.  Org-caldav's sync command is now deliberately disabled for this
calendar.

The replacement lives in =calendar-exchange.el=.  It uses org-caldav only for
iCalendar export/import conversion and implements its own href-aware state:

- Org =ID= remains stable.
- =EXCHANGE_HREF= stores DavMail's assigned resource URL.
- =EXCHANGE_ETAG= stores the last observed Exchange ETag.
- =EXCHANGE_REMOTE_UID= records the iCalendar UID independently.
- =~/.emacs.d/var/calendar-exchange/state.sexp= stores the last synchronized
  local hash, remote semantic hash, href, ETag, remote UID, and title.  It is
  mode 0600, data-only, and atomically replaced after each successful action.
- A changed ETag with unchanged remote content is accepted without rewriting
  Org, avoiding Exchange normalization churn.
- Conflicts stop the sync.  Deletions prompt in either direction.
- =jds/exchange-calendar-dry-run= displays a read-only plan.
- =jds/exchange-calendar-sync-entry= synchronizes only the entry at point.
- =jds/exchange-calendar-import-new= only imports untracked remote events.
- =jds/exchange-calendar-sync= runs the guarded full two-way sync.

The isolated integration test verified create, post-create ETag settling,
repeat no-op, local-to-remote update, remote-to-local update, remote import,
local-to-remote deletion, and remote-to-local deletion.  Both disposable test
events were removed afterward, leaving the Org file byte-for-byte equal to its
pre-test backup and =EmacsSync= empty.

The controlled migration then created all 12 local events.  A subsequent
read-only inventory and dry run reported exactly 12 local events, 12 remote
resources, 12 tracked mappings, and 12 =unchanged= actions.  After Exchange
finished processing the uploads, it revised all 12 ETags without changing
event content.  A guarded reconciliation fetched each resource, confirmed
that its semantic hash was unchanged, and updated only the mapping metadata
and state.  A final dry run again reported 12 =unchanged= actions; the
=calendar.org= buffer was saved and unmodified.

* Superseded design: direct org-caldav synchronization

Use =org-caldav= to synchronize the complete local calendar file with only the
dedicated =EmacsSync= Exchange calendar through the existing local DavMail
CalDAV gateway:

#+begin_example
calendar.org ↔ org-caldav ↔ localhost:1080 ↔ DavMail ↔ EmacsSync
default Exchange calendar → published ICS → get_exchange_cal.sh → cal-psu.org
#+end_example

The initial configuration should be deliberately narrow:

- Keep the existing Exchange-to-Org fetch unchanged.
- Configure =org-caldav-sync-direction= as =twoway= from the first sync and do
  not later switch this calendar between one-way and two-way modes.
- Pair only =calendar.org= with only the dedicated =EmacsSync= collection.
- Do not use =org-caldav-select-tags=.  A remote-created event imported into
  Org would not necessarily have the selection tag; omitting it from the next
  export could then look like a local deletion.
- Set both local-to-remote and remote-to-local deletion policies to =ask=.
- Initially allow remote changes to update only the Org title and timestamp,
  preserving local body text that cannot round-trip safely through iCalendar.
- Run pushes manually with =M-x org-caldav-sync= until the behavior has been
  observed and trusted.  Do not add startup, save, or periodic push hooks in
  the first implementation.
- Use =calendar.org= as both =org-caldav-files= and =org-caldav-inbox= so events
  created in Outlook's =EmacsSync= calendar are inserted into the same file.

Org-caldav will add stable =ID= or =UID= properties to synchronized entries and
maintain a separate state file.  Those identifiers and the state file are part
of the synchronization data and must be preserved.

* Decisions needed before implementation

** Resolved: which Exchange calendar receives events?

Use the dedicated =EmacsSync= calendar created in Outlook.  Do not point
org-caldav at the populated default Exchange calendar.

The configured DavMail collection URL has been verified against an
Outlook-created test event and maps to =EmacsSync=.

** Resolved: what is the synchronization unit?

Synchronize the whole of =calendar.org= with =EmacsSync=.  Do not use an
=:EXCHANGE:= selection tag in the two-way configuration.

This means the first sync is a migration: all exportable events already in
=calendar.org= will be uploaded to the initially empty =EmacsSync= calendar.
Review the local file and estimate that first-sync scope before running it.

** Resolved: where is org-caldav state stored?

The existing =no-littering= package redirects =org-caldav-save-directory= to
=~/.emacs.d/var/org/caldav/save/= and creates it when org-caldav loads.  Keep
that default for this single-machine setup; no additional calendar
configuration is needed.  The state file records UID, content hash, remote
ETag, sequence, status, and the previously synced files so org-caldav can tell
which side changed or deleted an event.  Preserve it alongside the Org backup
when recovering from a failed sync.

If another machine is later allowed to sync the same =calendar.org= and
=EmacsSync= calendar, revisit this decision: both machines would need a
carefully coordinated state strategy and must not sync concurrently.

** Resolved: authentication storage

Reuse the existing single-line encrypted password in
=~/.psu_mailpass.gpg=.  Immediately before =org-caldav-sync=,
=jds/calendar--install-davmail-auth= decrypts that file into a temporary buffer
and seeds Emacs's in-memory Basic-auth cache for =127.0.0.1:1080= and the
=DavMail Gateway= realm.  It does not create another persistent password copy
or log the plaintext.  The cache naturally disappears when Emacs exits.

An authenticated read-only request on 2026-10-05 returned HTTP 200 and zero
=VEVENT=s from the verified =EmacsSync= collection.  This confirms both the
credential bridge and the calendar's empty pre-sync state.  The new CalDAV
configuration was also evaluated in the running Emacs session; no restart is
required before the controlled first sync.

* Implementation outline

** Phase 1: validate DavMail CalDAV independently

1. Start DavMail using the existing Microsoft 365 configuration.
2. Verify that the local CalDAV endpoint responds on =127.0.0.1:1080=.
3. Discover or confirm the target calendar collection.  DavMail commonly uses
   the default collection shown below, but the named =EmacsSync= collection
   may be a subcollection and must be discovered rather than guessed:

   #+begin_example
   http://127.0.0.1:1080/users/ACCOUNT/calendar
   #+end_example

   Keep the actual account identifier out of tracked configuration where
   practical.
4. DONE: the Outlook-created =test= event was the sole event returned through
   the configured URL, confirming that it resolves to =EmacsSync=.
5. DONE: the user deleted =test= in Outlook and confirmed that =EmacsSync= is
   empty again.

** Phase 2: validate the guarded =org-caldav= configuration

A small =use-package org-caldav= block now exists in =calendar.el=.  It uses
the following settings:

#+begin_src emacs-lisp
(use-package org-caldav
  :commands org-caldav-sync
  :custom
  (org-caldav-url
   "http://127.0.0.1:1080/users/jds6696@psu.edu/calendar")
  (org-caldav-calendar-id "EmacsSync")
  (org-caldav-uuid-extension ".EML")
  (org-caldav-files '("~/Dropbox/org/calendar.org"))
  (org-caldav-inbox "~/Dropbox/org/calendar.org")
  (org-caldav-sync-direction 'twoway)
  (org-caldav-sync-changes-to-org 'title-and-timestamp)
  (org-caldav-delete-org-entries 'ask)
  (org-caldav-delete-calendar-entries 'ask)
  (org-caldav-backup-file "~/Dropbox/org/calendar-caldav-backup.org")
  (org-icalendar-timezone "Eastern Standard Time"))
#+end_src

Org-caldav combines the URL and calendar ID into the tentative collection URL
=http://127.0.0.1:1080/users/jds6696@psu.edu/calendar/EmacsSync/=.  Verify that
DavMail reports this collection as =EmacsSync= before invoking a sync; change
the base URL or calendar ID if DavMail exposes it under a different path.

Do not bind a key initially.  If a global leader binding is wanted after the
test period, add it to =bindings.el= rather than =calendar.el=.

** Phase 4: optional ergonomics

Only after the controlled tests succeed:

- Consider a command that pushes only the entry at point, if org-caldav offers
  a reliable public API for it.
- Consider a global leader binding in =bindings.el=.
- Keep automatic synchronization disabled unless manual use becomes tedious
  and failure behavior is well understood.

* Failure handling and rollback

- If Emacs startup is affected, remove or comment only the new guarded
  =use-package org-caldav= block.  The existing fetch path should remain
  independent.
- If the first sync targets the wrong calendar, stop immediately; do not run a
  second sync in an attempt to repair it.
- Restore remote data from the pre-test backup or, while it remains dedicated
  to this experiment, remove and recreate the =EmacsSync= calendar.
- Preserve a copy of org-caldav's state file before troubleshooting.  Do not
  delete its state and resync against a populated calendar: losing UID history
  can create duplicates or make deletions ambiguous.
- Never use =org-caldav-delete-everything= against a real Exchange calendar.

* Acceptance criteria

- Emacs starts normally when DavMail is stopped or org-caldav is unavailable.
- Existing exportable =calendar.org= entries are created exactly once in
  =EmacsSync= and nowhere else.
- An Outlook-created =EmacsSync= event is imported exactly once into
  =calendar.org= and remains stable across a second sync.
- Editing the entry updates it without duplication.
- Deletions prompt in both directions during the initial deployment.
- Times remain correct in =America/New_York=, including across DST.
- The existing =cal-psu.org= fetch still works.
- The Org agenda does not acquire duplicate representations unexpectedly.
- No credentials or private calendar URLs enter the Git repository.

* Alternative if org-caldav is unsafe or incompatible

Implement a narrow command that exports only the current Org subtree as an ICS
VEVENT and performs a CalDAV =PUT= through DavMail, storing the returned/stable
UID and remote URL as Org properties.  Add separate explicit update and delete
commands.  This requires more local code but has a smaller remote mutation
surface than synchronizing an entire file.

Microsoft Graph is the longer-term standards-based alternative, using
=Calendars.ReadWrite= and =POST /me/events=, but it introduces a separate OAuth
application and token lifecycle.  Prefer it only if PSU policy or DavMail
compatibility blocks the CalDAV approach.
